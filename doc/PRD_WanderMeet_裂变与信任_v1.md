## 1. 背景与目标

### 1.1 背景

- 微信小程序已上线；抖音小程序审核中；全国注册约百级，需从「有产品」进入「有增长、有信任」。
- 产品双主线：**城市大群**（全国目录、低门槛弱连接）+ **线下活动**（高意图见面）。
- 现有能力：登录/资料、活动流、报名、群聊、举报/拉黑、组织者认证（`user_verifications` 人工审核为主）、Premium 占位（`enabled=false`）。
- **缺失**：邀请归因、权益发放、见面打卡互评、曝光加权、照片验证、统一信任展示、见面安全动线。

### 1.2 产品目标

| 目标 | 说明 | 核心指标 |
|------|------|----------|
| **增长** | 通过可验证的邀请裂变，提高北京等种子城市的有效新用户 | 有效邀请率、K-factor（按城市） |
| **信任** | 让独行/旅居用户感知「真人、可见面、有规则」 | 照片验证率、信任标签曝光点击率 |
| **留存** | 见面后互评解锁权益，形成闭环 | 打卡率、互评完成率、7 日留存 |
| **供给** | 激励组织者拉新并获得曝光，改善「有局可报」 | 组织者拉新数、加权活动报名率 |

### 1.3 设计原则

1. **奖励绑定有效行为**：仅注册不计奖；加群或报名计奖。
2. **权益虚拟化**：7/15 天「高级功能」以**权益包**实现（置顶、徽章、展示增强），V1 不做现金返利、不做提现。
3. **信任可见、验证可选**：不挡浏览；在高意图节点（报名、私聊、发局）强引导照片验证；实名可选。
4. **裂变绑同城社交**：话术与机制围绕「进群 / 参加活动」，不做 dating 导向。
5. **差评不公开**：互评影响信任分，不对他人展示星级，降低撕逼与合规风险。
6. **一套信任分**：邀请、验证、见面、举报统一汇入信任档案，避免多套体系。

### 1.4 成功标准（上线后 8 周，北京单城参考）

- 有效邀请占全部邀请绑定的 **≥ 40%**。
- 照片验证用户占活跃报名用户的 **≥ 25%**。
- 已结束活动中，双方打卡+互评完成率 **≥ 30%**（初期官方局可人工助推）。
- 因信任/安全相关举报率不高于基线 **1.5 倍**（监控误伤）。

## 2. 范围

### 2.1 本版做（In Scope）

| 模块 | 能力 |
|------|------|
| 邀请裂变 | 邀请码/小程序码、归因绑定、有效邀请判定、阶梯奖励、新人礼包 |
| 权益包 | 限时 Premium 能力、置顶次数、徽章、权益台账与过期 |
| 见面闭环 | 活动结束打卡、双向互评、见面权益解锁、见面次数展示 |
| 组织者曝光 | 有效邀请达标 → 活动列表加权与角标 |
| 信任中心 | 信任等级、照片验证、实名（可选）、资料完整度 |
| 安全 | 报名安全须知、活动前提醒、群置顶安全卡片、独行安全指南页 |
| 运营 | 简易后台/脚本：邀请异常、验证审核、权益补发 |

### 2.2 本版不做（Out of Scope）

- 现金红包、提现、分销多层级佣金。
- 复杂付费会员 SKU 与微信支付订阅（权益包为赠送，不接支付）。
- GPS 围栏强制打卡（V1 不做；预留扩展字段）。
- 公开用户星级/差评墙。
- 1v1 匹配算法、滑动交友。
- 全国多城运营策略与本地化运营位（仅实现能力，运营先聚焦北京）。

## 4. 核心概念

| 术语 | 定义 |
|------|------|
| **邀请人** | 分享邀请码/链接的用户 |
| **被邀请人** | 通过邀请渠道首次登录并完成绑定的用户 |
| **有效邀请** | 被邀请人在绑定后 7 日内完成「有效动作」的邀请关系 |
| **有效动作** | 加入任意 **1 个城市大群**，或 **报名任意 1 场活动**（含城市大群视为活动 `city_hall`） |
| **权益包** | 有时效的一组虚拟能力（置顶次数、Premium 标记、展示位等） |
| **信任等级** | 由资料、照片验证、实名、见面、举报合成的对外展示档位 |
| **成功见面** | 同一场 `event` 活动中，双方均到场打卡且完成互评 |
| **曝光加权** | 活动列表排序中的临时加分与角标，有时效、有上限 |

## 5. 模块一：邀请裂变

### 5.1 功能概述

用户生成专属邀请渠道，被邀请人完成有效动作后，邀请人获得阶梯奖励；被邀请人获得新人礼包。邀请关系永久绑定（首个有效邀请人获胜，不可改绑）。

### 5.2 邀请归因

#### 5.2.1 渠道形态

| 形态 | 说明 |
|------|------|
| 邀请码 | 6 位大写字母+数字，用户唯一，可手动输入（备用） |
| 小程序路径 | `/pages/entry/entry?inv={code}` 或统一 landing 页携带 `inv` |
| 小程序码 | 后端或微信 API 生成，scene 携带 `inv` |
| 分享卡片 | 标题/封面可配置，默认「来旅聚，加入同城大群」 |

#### 5.2.2 绑定规则

1. **新用户**：首次手机号登录成功后，若 URL/scene 含 `inv`，写入 `referral_bindings`（status=`pending`）。
2. **老用户**：若已存在绑定（任意状态），**忽略**新 `inv`，不覆盖。
3. **自邀**：邀请码归属与当前用户相同 → 不绑定。
4. **循环邀**：A 邀 B 后，B 再邀 A → 仅 A→B 计 1 次有效邀请（双向各算各自作为邀请人的新用户 C、D…）。
5. 绑定后写入 `users.acquisition_source = referral:{code}`（与现有字段兼容）。

#### 5.2.3 有效邀请判定

被邀请人 binding 为 `pending` 时，在 **绑定时刻起 7×24h 内** 首次发生以下任一事件 → 置 `qualified`，记录 `qualified_action`（`city_hall_join` | `event_enroll`）与 `qualified_at`：

- 调用 `POST /city-groups/join` 成功；
- 调用活动报名成功（含 `city_hall` 与 `event`）。

超时未发生 → `expired`，邀请人不获得该条奖励（可展示「好友尚未完成首次参与」）。

#### 5.2.4 奖励发放时机

- 状态变为 `qualified` 后 **24h** 发放（T+1），便于反作弊抽查。
- 发放时若邀请人账号 `status!=active` → 暂缓，人工处理。
- 发放写入 `user_entitlements` / `user_badges`，并推送系统通知（模板消息/站内）。

### 5.3 邀请人奖励阶梯

| 累计有效邀请（终身，可重复达标仅首次） | 奖励 |
|----------------------------------------|------|
| 1 | 权益包 **7 天**（标准版） |
| 3 | 权益包 **15 天**（标准版）+ 徽章 **引路人** |
| 5 | 权益包 **15 天** + **活动置顶 1 次**（24h，需手动选用活动） |
| 10 | 权益包 **30 天** + 徽章 **同城使者** |

**叠加规则**：达到新阶梯时，发放**该阶梯新增部分**（不重复发已发过的同级权益）；权益时长在已有未过期权益上**延长**（同类型取 max 结束时间 + 新增天数）。

**照片验证加成**：邀请人已通过照片验证时，本次发放的权益包时长 **×1.2**（向上取整到天）。

**未照片验证邀请人**：单日通过审核的有效邀请奖励 **上限 3 条**（防刷）。

### 5.4 被邀请人新人礼包

绑定且 7 日内完成有效动作后发放：

- 权益包 **3 天**（轻量版：仅展示增强，不含置顶）；
- 个人页 **新人** 标签（7 天自动消失）；
- 可选：北京等运营配置城市，首页插入 1 次「新手友好活动」推荐位（运营配置 activityId 列表）。

### 5.5 页面与交互

#### 5.5.1 我的 → 邀请好友

| 区块 | 内容 |
|------|------|
| 头部 | 累计有效邀请数、待生效（pending）数、下一档进度条 |
| 主按钮 | 分享给微信好友 / 生成海报 |
| 邀请码 | 展示 + 复制；说明「好友注册后 7 天内加群或报名即算成功」 |
| 奖励说明 | 阶梯表（5.3） |
| 记录列表 | 最近 20 条：昵称脱敏、状态（待完成/已生效/已过期）、时间 |

#### 5.5.2 触发入口（弱引导）

- 首次加入城市大群成功页：「邀请同城旅友」按钮。
- 活动报名成功页：「分享给可能同行的人」。
- 信任中心：验证通过后提示「验证用户邀请奖励 +20% 时长」。

### 5.6 分享文案（默认）

> 我在用「旅聚」找同城旅友～加入城市大群或一起参加线下小活动，公共场所见面更安心。微信搜「旅聚」或点链接：[小程序]

## 6. 模块二：权益包与徽章

### 6.1 权益包类型

| 类型 ID | 名称 | 时长 | 包含能力 |
|---------|------|------|----------|
| `premium_lite_3d` | 新人轻量 | 3 天 | `premium_badge` |
| `premium_std_7d` | 标准 7 天 | 7 天 | 下表标准能力 |
| `premium_std_15d` | 标准 15 天 | 15 天 | 标准能力 |
| `premium_std_30d` | 标准 30 天 | 30 天 | 标准能力 |

**标准能力（standard）**：

| 能力键 | 说明 |
|--------|------|
| `premium_badge` | 资料页/公开展示 **旅聚+** 角标 |
| `activity_pin` | 活动置顶次数（按发放时写入 `pin_quota`） |
| `profile_highlight` | 公开展示页多一行权益装饰（非付费色条） |

**置顶使用规则**：

- 用户对**自己组织的、状态为 published 的 event** 消耗 1 次 `activity_pin`；
- 置顶持续 **24h**，同一用户同时最多 **1 场** 活动处于置顶；
- 置顶活动列表排序 **+加权分**（见模块四），并显示角标 **「置顶」**。

### 6.2 徽章

| badge_id | 名称 | 获得条件 | 展示 |
|----------|------|----------|------|
| `referrer_guide` | 引路人 | 有效邀请 ≥3 | 资料页、公开展示 |
| `referrer_ambassador` | 同城使者 | 有效邀请 ≥10 | 同上 |
| `meet_first` | 见过面 | 首次成功见面互评 | 同上 |
| `meet_regular` | 常出门 | 成功见面 ≥5 | 同上；可选展示见面次数 |

用户可在 **我的 → 信任中心 → 徽章** 中选择隐藏部分徽章（默认展示）。

### 6.3 Premium 接口演进

`GET /me/premium` 响应扩展（兼容旧客户端）：

```json
{
  "enabled": true,
  "sku": [],
  "entitlement": {
    "active": true,
    "tier": "standard",
    "expiresAt": "2026-06-01T00:00:00Z",
    "pinQuotaRemaining": 1,
    "badges": ["referrer_guide"]
  }
}
```

无权益时 `enabled=false`，`entitlement.active=false`。

## 7. 模块三：见面打卡与互评

### 7.1 适用范围

- **仅** `activity_kind = event` 的线下活动。
- **不含** 城市大群 `city_hall`。
- 用户须为该活动 `activity_enrollments.status = joined`。

### 7.2 时间窗口

| 节点 | 规则 |
|------|------|
| 窗口开启 | `activity.start_at + 2h` |
| 窗口关闭 | `min(activity.end_at + 24h, start_at + 72h)`；若 `end_at` 为空，取 `start_at + 48h` |
| 提醒 | 窗口开启时推送「见面打卡」；关闭前 6h 未打卡再提醒 1 次 |

### 7.3 打卡流程

1. 用户在 **我的活动 → 待打卡** 或 push 进入打卡页。
2. 展示活动信息、参与人列表（仅 **已报名且 joined** 的用户）。
3. 用户点击 **「我已到场」** → 写入 `activity_checkins`（`checked_in_at`）。
4. **V1 不要求 GPS**；可选上传 1 张现场图（不公开，仅风控/申诉，上限 1 张，走 BOS 私有或现有 chat 上传策略）。

### 7.4 互评流程

打卡后，对**同活动其他已打卡用户**展示互评页（每次 1 人，可跳过）：

| 字段 | 类型 | 必填 |
|------|------|------|
| `met` | bool | 是 — 是否见到对方 |
| `tags` | enum[] | 见到时选，最多 3：`punctual` 准时、`friendly` 友善、`would_meet_again` 适合再约、`would_not_meet_again` 不推荐再约 |
| `comment` | string | 否，≤50 字 |

**规则**：

- 对同一人互评 1 次，提交后不可改（申诉走举报）。
- **`met=false`**：不计入成功见面；累计被多人标记且信任分低于阈值 → 限制主动发起私聊（见 8.4）。
- **互评内容不对其他用户公开展示**；仅聚合为信任分与见面次数。

### 7.5 成功见面定义

对用户 A、B 在同一 `activity_id`：

1. A、B 均有 `activity_checkins`；
2. A 对 B、B 对 A 的互评均已提交；
3. 双方互评 `met=true`。

满足则各记 **1 次成功见面**，触发见面权益（7.6）。

### 7.6 见面权益

| 条件 | 奖励（各用户终身首次达标发放） |
|------|--------------------------------|
| 首次成功见面 | 徽章 **见过面** + 权益包 **3 天**（标准版） |
| 累计成功见面 3 次 | 权益包 **7 天** |
| 累计成功见面 5 次 | 徽章 **常出门** |

### 7.7 见面次数展示

- `GET /users/{id}/public` 增加 `meetCount`（成功见面次数）、`showMeetCount`（默认 true，本人可关）。
- 活动详情组织者区块、群成员列表：展示 **照片验证**、**见过面 N 次**（当 `showMeetCount=true` 且 N≥1）。

### 7.8 页面

| 页面 | 说明 |
|------|------|
| 打卡页 | 活动摘要、到场按钮、参与人、安全提示链接 |
| 互评页 | 逐人卡片、标签 Chips、提交 |
| 我的 → 见面记录 | 列表：活动名、时间、成功/未完成 |

## 8. 模块四：组织者邀请曝光

### 8.1 统计口径

组织者的 **累计有效邀请数**（作为邀请人，status=qualified 且已发放），与模块一一致，终身累计。

### 8.2 曝光奖励阶梯

| 组织者累计有效邀请 | 奖励 |
|--------------------|------|
| 3 | 下一场自行发布的 `event` 获得 **24h 列表加权** + 角标 **组织者推荐** |
| 5 | **48h 加权** + 发现页 **1 次固定推荐槽**（按用户当前城市/北京兜底，运营可配） |
| 10 | **7 天内**发布的前 **2 场** `event` 各 **48h 加权** |

**与置顶关系**：置顶（权益包）与组织者加权 **可叠加**，但同一活动同时仅 1 种加权来源显示主角标（置顶优先展示）。

### 8.3 列表加权算法（V1）

活动排序分：

```
score = base_time_score + trust_organizer + exposure_boost + pin_boost
```

| 因子 | 说明 |
|------|------|
| `base_time_score` | 现有「今天/明天/距离」逻辑，不变 |
| `trust_organizer` | 组织者信任等级加分（见 9.3） |
| `exposure_boost` | 模块四发放的加权，随剩余时间衰减 |
| `pin_boost` | 用户消耗置顶次数后的固定加分 |

加权记录表 `activity_exposure_boosts`：`activity_id`、`boost_type`（organizer_tier / pin / discover_slot）、`starts_at`、`ends_at`、`weight`。

### 8.4 发布页展示

- 发布活动页底部：**「邀请好友，解锁活动曝光」** 进度条（3/5/10）。
- 组织者 **我的** 页：累计有效邀请、当前可用曝光权益摘要。

## 9. 模块五：信任中心

### 9.1 信任等级（对外）

| 等级 | 内部键 | 条件 | 展示文案 |
|------|--------|------|----------|
| 1 | `basic` | 仅登录 | 已注册 |
| 2 | `profile_complete` | 头像+昵称+简介+≥1标签 | 资料完整 |
| 3 | `photo_verified` | 照片验证通过 | **照片已验证** |
| 4 | `realname_verified` | 实名认证通过（现有 verification approved） | 实名已验证 |

**展示等级** = 满足条件的**最高档**（非累加图标墙）。等级 3、4 在资料页、活动详情、群成员列表展示对应角标。

### 9.2 照片验证

#### 9.2.1 流程

1. **信任中心 → 照片验证** 或 报名前引导弹层（可跳过）。
2. 调起相机 **现场自拍**（禁止相册，小程序 `chooseMedia` sourceType=camera）。
3. 上传至私有 bucket；与当前 `avatar_url` 比对：
   - **V1 方案 A（推荐初期）**：人工审核队列，24h 内出结果；
   - **V1 方案 B**：接第三方人脸比对 API（腾讯云/阿里云），置信度 ≥ 阈值自动通过，否则转人工。
4. 结果：`photo_verifications.status` = pending / approved / rejected。

#### 9.2.2 与组织者认证关系

- **发活动认证**（现有 `user_verifications`）与 **照片验证** 拆分字段：
  - `verificationBadge`：组织者实名认证通过（发局用，逻辑保持）；
  - `photoVerified`：参与者/组织者均可做，用于信任展示。
- 发活动门槛（维持产品现状）：**组织者认证通过** 可发局；照片验证 **不强制** 但强引导，未验证发局时列表排序略降。

#### 9.2.3 引导触点

| 触点 | 行为 |
|------|------|
| 首次报名 event | 弹层说明 + 「去验证」/「稍后再说」 |
| 首次发起私聊申请 | 未验证时提示，**不阻断** |
| 邀请好友页 | 已验证显示 +20% 奖励说明 |

### 9.3 实名（可选）

- 沿用 `GET/POST /me/verification`，文案改为 **「实名认证（可选）」**。
- **普通参与者报名 event / 加群：不要求实名**。
- **发活动**：要求 `user_verifications.status=approved`（现有逻辑）或运营后台白名单。
- 实名通过 → 信任等级 4；可与照片验证并存。

### 9.4 信任分（内部）

内部数值 `trust_score`（0–1000，用户不可见），用于排序与风控：

| 事件 | 分值变化 |
|------|----------|
| 资料完整 | +50 |
| 照片验证 | +150 |
| 实名 | +100 |
| 成功见面 1 次 | +30（上限 +300） |
| 有效邀请 1 人 | +20（上限 +200） |
| 被举报成立 1 次 | -100 |
| 互评「不推荐再约」被≥3人选择（90 天） | -80 |
| 互评 met=false 被≥2人（90 天） | -120，触发私聊限制 |

**私聊限制**：`trust_score < 400` 时，不可 **主动发起** 新私聊申请（可回复已有 thread）。

├── 实名认证（可选，入口与状态）

## 11. 模块六：见面安全

### 10.1 安全内容（固定文案，运营可配置）

**报名前须知（首次报名 event 强制勾选）**：

1. 尽量在 **公共场所** 见面，首次避免私密场所。
2. **不要** 向陌生人私下转账或预付大额费用。
3. 告知亲友行程；感觉不适可退出并 **举报**。

勾选记录写入 `user_safety_ack`（user_id, ack_type=enroll, ack_at）。

### 10.2 触点

| 时机 | 形式 |
|------|------|
| 首次报名 | 全屏须知 + 勾选 |
| 活动开始前 2h | 订阅消息（若授权）：时间地点 + 1 条安全短句 |
| 活动群创建/加入 | 系统消息插入 **安全卡片**（不可删，可折叠） |
| 打卡页 | 「安全指南」链接 |
| 我的 → 信任中心 | 《独行出行安全指南》长文 |

### 10.3 《独行出行安全指南》结构

1. 见面地点怎么选（地铁口、商场、连锁咖啡）
2. 独行赴约前告知亲友
3. 费用 AA 与防诈骗
4. 不适时如何举报/拉黑
5. 平台能力说明（认证、举报、不展示差评）

### 10.4 「需要帮助」

打卡页底部 **「一切正常 / 需要帮助」**：

- 一切正常：无操作；
- 需要帮助：展示运营微信与 **110/120** 提示（纯信息，V1 不接入报警 API）。

## 12. 反作弊与合规

### 11.1 邀请反作弊

| 规则 | 处理 |
|------|------|
| 同设备多号 | 同 device_fingerprint 24h 内 >3 次注册，不计有效邀请 |
| 同 IP 异常 | /24 网段 1h 内 >10 次绑定，标记 audit，延迟发放 |
| 批量虚拟号 | 短信渠道风险号段，不计奖 |
| 自邀、互刷 | 见 5.2.2 |
| 邀请人被封 | 未发放奖励撤销；已发放权益可冻结 |

device_fingerprint：小程序端上报 `deviceId`（现有或新增轻量 SDK），服务端存储 hash。

### 11.2 打卡/互评反作弊

- 同活动同对用户互评仅 1 次；
- 活动未开始不可打卡；
- 组织者不能对未报名用户互评；
- 互评提交频率：1 分钟 ≤5 次 → 429。

### 11.3 微信合规

- 不使用 **诱导分享** 强制性关卡（分享不作为报名前置条件）；
- 奖励描述避免「现金」「躺赚」；
- 订阅消息仅活动/打卡/验证结果，需用户授权。

### 11.4 隐私

- 自拍原图仅审核/风控可见，不公开展示；
- 互评原文不公开；
- 邀请记录对他人不可见。

## 20. 验收标准

### 19.1 邀请

- [ ] 新用户带 `inv` 登录后生成 binding，老用户不覆盖。
- [ ] 7 日内加群或报名 → qualified；仅注册 → expired。
- [ ] 阶梯 1/3/5/10 奖励正确发放，照片验证 +20% 时长。
- [ ] 邀请页展示进度与记录。

### 19.2 权益

- [ ] `/me/premium` 反映 active 权益与 pin 次数。
- [ ] 置顶 24h 且单用户单活动置顶互斥。

### 19.3 见面

- [ ] 仅 event 可打卡；窗口外不可提交。
- [ ] 双方 met=true 互评后 meet_count+1，权益触发。
- [ ] 互评内容不在公开 API 返回。

### 19.4 组织者曝光

- [ ] 有效邀请 3/5/10 触发对应 boost，过期后排序恢复。

### 19.5 信任与安全

- [ ] 照片验证通过后 photoVerified、trust_level 更新。
- [ ] 实名可选，不阻断普通报名。
- [ ] 首次报名须勾选安全须知。
- [ ] 信任中心、安全指南可访问。

### 19.6 反作弊

- [ ] 自邀不计；未验证邀请人日 cap 生效。

## 21. 产品决策记录（拍板结论）

以下 4 项为需产品负责人确认的问题，**本 PRD 按下列结论执行**：

| # | 问题 | **拍板结论** | 理由 |
|---|------|--------------|------|
| 1 | **有效邀请**是否包含「仅加城市大群」？ | **包含**。加任意 1 个城市大群 **或** 报名任意 1 场活动（含 city_hall / event）均算有效动作。 | 符合「全国城市大群」产品主线；北京冷启动阶段加群门槛低于发局，利于裂变；与主播话术一致。 |
| 2 | **见面打卡** V1 是否要求 GPS？ | **不要求**。双方点击「我已到场」+ 完成互评即可；现场图可选上传，仅风控用。 | 室内定位差、实现成本高；100 用户阶段优先跑通闭环与信任叙事；GPS 留作后续加分项非阻断。 |
| 3 | **互评差评**是否对他人可见？ | **不可见**。互评不返回给第三方；仅聚合为内部信任分、见面次数与风控规则（如私聊限制）。 | Solo 用户要「安全感」而非「公开打分」；降低冲突与合规风险；对标 NomadTable 类体验偏线下而非 Yelp。 |
| 4 | **实名**是否与普通参与者报名绑定？ | **不绑定**。普通用户加群、报名 **不要求实名**；**发活动**仍要求组织者 `user_verifications` 审核通过；实名为信任等级可选增强项。 | 降低首次转化摩擦；独行用户可先照片验证再深度信任；发局门槛保证供给侧质量。 |

**补充拍板（实现细节）**：

| 项 | 结论 |
|----|------|
| 奖励形式 | 仅虚拟权益包与徽章，无现金 |
| 邀请绑定 | 首个 inviter 永久有效，不可改绑 |
| 照片验证 vs 发局认证 | 字段拆分：photoVerified 全员可选；verificationBadge 组织者发局 |
| 城市大群打卡 | 不做见面互评，避免大群场景滥用 |
