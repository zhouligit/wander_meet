# WanderMeet「城市大群」产品需求与接口 / 技术规划

更新时间：2026-05-13  
状态：**规划文档**（尚未在代码中实现；评审通过后按迭代拆解）

本文档合并：**产品需求**、**后端表与接口规划**、**性能与优化方案**（含与现有 `activity_messages`、`/me/chats` 未读逻辑的衔接）。

---

## 1. 背景与目标

### 1.1 问题

用户「当前在某城」或「计划去某城」时，缺少与城市同路人的**持续弱连接**场域。活动为强场景、相对低频；**城市大群**可承接问路、拼饭、找搭子、同城动态，并导流至活动与私聊。

### 1.2 目标（指标在立项时量化）

- 提升「到城 / 计划到城」用户的 **首日 / 7 日留存**。
- 提升 **活动曝光与报名**（群内运营位、活动卡片等，二期）。
- 控制 **同城多群分裂** 与 **冷启动空城** 成本。

### 1.3 参考语境

产品信息架构与体验预期可参考 NomadTable 类「城市桌 / 同城圈子」心智；与现有 **活动群聊**（`activities` + `activity_messages`）需在命名与入口上区分，避免用户混淆。

## 2. 核心概念（需评审拍板）

| 项 | 说明 |
|----|------|
| **城市** | 与现有 `city_code`、城市选择器一致；MVP 建议 **一市一群**（一个 `city_code` 对应一个官方城群会话）。 |
| **城群 vs 活动** | 城群是**城市级公共会话**；活动仍是独立实体。是否用「特殊活动」承载城群见 **§7.1 数据模型选项**。 |
| **成员** | 用户「加入城群」产生成员关系；与 **活动报名**、**私聊** 权限模型区分。 |

**待拍板**

1. **一城一群** vs **一城多群 + 指定主群**。  
2. **无群时**：用户手动创建 / 系统自动建 / 仅运营白名单可建。  
3. **加入门槛**：是否要求手机号已验证、实名（与风控策略一致）。

## 3. 用户场景与流程

### 3.1 触发「推荐加入城群」的条件（满足其一即可，可组合）

- **定位所在城市**（用户授权定位后解析为 `city_code`）。
- **资料 / Onboarding** 中的「当前所在城市」「计划停留城市」等已有字段。
- **手动选择「关注城市」**（不依赖定位）。

**规则**

- 多城并存时的 **优先级**（例如：定位城 > 资料当前城 > 手动列表）需写死或配置化。  
- **隐私**：未授权定位时，不得静默用 IP 猜城；若使用须在隐私政策中说明。

### 3.2 该城已存在大群

- 展示推荐卡片：城市名、群简介、成员规模（可选）、主按钮 **「加入城市大群」**。  
- 加入成功：**进入城群会话** 或 **留在当前页 + 弱提示**（二选一，交互定稿）。

### 3.3 该城尚不存在大群

- 按 §2 已选策略：**创建 + 推荐加入** 或 **仅展示「即将开通」+ 订阅通知**（若不允许用户建群）。  
- 创建者默认进群（若允许用户创建）。

### 3.4 打扰控制

- 同一 `city_code`、同一用户 **7 天内推荐次数上限**（可配置）。  
- 与现有推送 / 站内通知策略对齐，避免多入口重复弹窗。

## 4. 入口与信息架构

| 入口 | 说明 |
|------|------|
| **首页 / 发现** | 固定「城市圈子」或「同城大群」入口。 |
| **城市选择结果页** | 选城后若未加入该城群 → 底部条 / 半屏推荐。 |
| **个人资料 / 旅行状态** | 保存城市后触发推荐链路。 |
| **活动详情** | 活动 `city_code` 对应城群未加入时，弱提示加入同城大群。 |
| **消息 Tab** | 「城市群」子列表或置顶会话（与活动会话列表并存时的排序规则需定义）。 |

---

## 5. 功能范围（MVP / 二期）

### 5.1 MVP

- 城市 ↔ 城群 **一对一**（或明确「主群」语义）。  
- 加入 / 离开城群；城内 **文本消息**（图片二期可与活动消息对齐）。  
- 推荐卡片数据接口（是否已存在群、当前用户是否已加入）。  
- 建群策略按 §2 定案后实现其一。

### 5.2 二期

- 群公告、置顶、管理员、踢人 / 禁言。  
- 活动卡片分享进城群、小程序分享进群。  
- 同城话题 / 新人引导；运营后台 **合并 / 解散误建群**。  
- 与活动群的 **一键发布活动** 导流。

---

## 6. 治理与合规

- 举报入口与现有 **举报** 体系打通。  
- 内容安全策略（敏感词、频次限制）与活动消息一致或更严。  
- 群解散、合并、封禁的 **运营后台** 能力占位。

## 7. 后端：数据模型与现有表关系

### 7.1 数据模型选项（必选其一，影响接口与迁移）

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 虚拟活动承载城群** | 每城在 `activities` 插入一条「系统城群」活动（如固定 `category_id` / `activity_status` 标记），沿用 `activity_enrollments` + `activity_messages` + 现有拉消息接口。 | 复用现有 IM 接口与成员校验，开发量小。 | 活动列表需过滤城群；`organizer_id` 语义需约定为平台账号；与真实活动混排需小心。 |
| **B. 独立城群表 + 独立消息表** | 如 `city_groups`、`city_group_memberships`、`city_group_messages`。 | 语义清晰，活动与城群完全解耦。 | 新接口多一套；未读、会话列表需与 `/me/chats` 合并或分叉。 |
| **C. DM 线程承载** | 每城一个「广播型」`dm_threads` + `direct_messages`。 | 复用私聊基础设施。 | 群模型与现有多为 1v1 私聊的语义可能冲突，需扩展线程类型。 |

**建议**：MVP 倾向 **方案 A 或 B**；若短期要上线且少改动，**A**；若长期城市运营重、活动与城群产品边界清晰，**B**。

### 7.2 与「活动表」体量

- `activities` 仅增加 **每城少量元数据行**，**不会因城群聊天变多而膨胀**。  
- 压力主要在 **消息表行数** 与 **会话列表 / 未读聚合**（见 §9）。

## 8. 接口规划（草案路径，前缀均为 `/api/v1/wm`）

以下路径与命名遵循现有 **camelCase 响应**、**Bearer 鉴权** 习惯；具体字段以 OpenAPI / 评审为准。

### 8.1 城市与城群元数据

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/city-groups/by-city-code/{cityCode}` 或 `/city-groups/lookup?cityCode=` | 返回：是否存在城群、`cityGroupId`、展示名、成员数（可选）、`joined` 是否已加入。供首页 / 选城后推荐卡片使用。 |
| `POST` | `/city-groups` | **创建城群**（若产品允许用户创建）：body 含 `cityCode` 等；返回城群 id 与默认会话信息。需鉴权 + 风控（频控、重复城校验）。 |
| `POST` | `/city-groups/{cityGroupId}/join` | 加入城群（写成员关系；若方案 A 则同步写 `activity_enrollments`）。 |
| `POST` | `/city-groups/{cityGroupId}/leave` | 离开城群；与「发起人不能退活动报名」类规则区分，城群允许离开。 |

**说明**：若采用方案 A，可对前端 **透明映射**：`cityGroupId` 与内部 `act_{id}` 二选一暴露，避免两套 ID；文档中需固定一种。

### 8.2 消息（依赖 §7.1）

- **方案 A**：继续复用  
  - `GET /activities/{activityId}/messages`  
  - `POST /activities/{activityId}/messages`  
  城群仅 `activityId` 指向系统城群活动。  
- **方案 B**：新增  
  - `GET /city-groups/{cityGroupId}/messages?cursor=&limit=`  
  - `POST /city-groups/{cityGroupId}/messages`  
  与活动消息字段对齐（`msgType`、`text`、`imageUrl`、`createdAt` 等）。

### 8.3 会话列表与「我的聊天」

| 类型 | 路径 | 说明 |
|------|------|------|
| **改造** | `GET /me/chats` | 在列表中 **合并** 城群会话与活动会话：排序键（最后消息时间）、预览文案、未读数。若方案 B，需联查 `city_group_messages` 或维护汇总表。 |
| **可选新增** | `GET /me/chats/summary` 或 query 参数 `includeCityGroups=true` | 若担心破坏兼容，可先加参数渐进发布。 |

### 8.4 已读 / 未读

| 类型 | 路径 | 说明 |
|------|------|------|
| **改造** | 与 `UserChatRead` 对齐的已读上报 | 方案 A：沿用活动维度 `last_read_message_id`；方案 B：`city_group_reads` 或在 `user_chat_reads` 扩展 `city_group_id`（二选一，避免重复全表扫描逻辑）。 |
| **优化** | 见 §9.2 | 大群未读不建议长期依赖「全表 COUNT」**。 |

### 8.5 Meta / 配置（可选）

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/meta/city-groups` 或并入现有 `/meta/...` | 前端展示用：推荐文案、是否开放用户建群、频控提示等（可静态配置 + 远端开关）。 |

### 8.6 管理端（二期）

- `GET/POST/PATCH` 运营后台：解散群、合并城、封禁城群消息等（可挂在现有 `admin` 路由下，路径另定）。

## 9. 性能与优化方案

### 9.1 单会话历史拉取（`activity_id` + 游标）

- 现有模式：`WHERE activity_id = ? AND id < ? ORDER BY id DESC LIMIT n` **可扩展**，单城消息量很大时仍以 **索引 + 分页** 为主。  
- **建议**：为 `activity_messages` 增加或确认 **`(activity_id, id)` 联合索引**（方向与排序一致），减少回表与 filesort。  
- **方案 B** 的 `city_group_messages` 同样建 **`(city_group_id, id)`**。

### 9.2 会话列表与未读（高风险点）

当前 `GET /me/chats` 对「当前页涉及的 `activity_id`」会做 **未读条数聚合**（`ActivityMessage` 与 `UserChatRead` 关联后对 `id > last_read_message_id` 做 `COUNT`）。对 **消息量极大的城群**，若用户长期未打开、`last_read_message_id` 滞后，可能导致 **对大段历史消息扫描**，CPU 与慢查询先于「单页拉消息」暴露。

**优化方向（按优先级，可与产品联合取舍）**

1. **大群未读单独策略**：例如仅展示 `99+`、或只比较「最后一条消息 id」与 `last_read` 的差值用 **估算**（需产品接受近似）。  
2. **计数下沉 Redis**：发送消息时 `INCR` 未读、进入会话 `DEL/SET`；列表接口读 O(1)（需处理多端一致与降级）。  
3. **异步维护汇总表**：如 `conversation_stats(activity_id, last_message_id, unread_count_hint, updated_at)`，由写入路径或队列更新。  
4. **冷热拆分**：历史消息归档到 `activity_messages_archive`，主表只保留近 N 天（架构成本高，后期再做）。  
5. **读写分离**：读多写少时，列表与历史查询走只读副本（运维与一致性另文）。

### 9.3 写入与连接池

- 城群高峰 **INSERT** 压力：监控 MySQL QPS、InnoDB 行锁；应用侧 **连接池** `pool_size` / `max_overflow` 与 **worker 数** 对齐文档 `.env.example` 说明。  
- 可选：**单城消息写入限流**（防刷屏），与风控联动。

### 9.4 监控与验收

- 接口：`p95` / `p99` 延迟（`GET /me/chats`、`GET .../messages`）。  
- DB：慢查询日志、**未读相关 SQL** 的执行计划抽检。  
- 业务：城群 DAU、消息量 / 日、列表接口错误率。

---

## 10. 依赖与风险

- **IM 形态**：当前为接口拉取；城群会放大 **轮询 / 列表合并** 频率，需评估是否引入 **WebSocket / 第三方 IM**（与全局路线图一致）。  
- **与活动混排**：方案 A 需在活动列表、地图等场景 **稳定过滤** 城群活动，避免污染「真实活动」列表。  
- **合规**：同城陌生人、群内容审核与日志留存策略。
